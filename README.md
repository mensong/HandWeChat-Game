# 微信群社交游戏服务

基于 `接口方案.md` 中的 HandWeChat HTTP API 实现的群聊社交游戏，包含
**金币系统、魅力系统、礼物系统、奴隶系统**。完整需求规格见
`微信群社交游戏-开发Prompt.md`。

## 运行环境

- Windows 10/11，与微信、HandWeChat API 服务同机运行
- Python 3.11+，运行时依赖 `websockets`（见 `requirements.txt`），测试需要 pytest

## 启动

1. 安装依赖：

```bash
pip install -r requirements.txt
```

2. 启动 HandWeChat API 服务（监听 `http://127.0.0.1:8000`）。
3. 微信登录，并保持目标群聊在当前聊天窗口打开。
4. 启动游戏服务：

```bash
python -m game.main --config config/game_config.json --db data/game.db --log-dir data/logs
```

5. 服务启动后会自动：等待微信在线 → 启动 OCR 监听 → 建立
   `WS /api/v1/ws/messages` 长连接实时接收新消息（连接建立前的历史消息不回补）。
   每批只处理 `is_latest` 的那条（不看 `confidence`），其余跳过；整帧没有
   `is_latest` 字段（API 未升级）时整帧丢弃。
6. **Web 控制台**：`http://127.0.0.1:8001/`（`web_host` 默认 `0.0.0.0`，局域网
   可通过本机 IP:8001 访问）：
   - **玩家数据**：各群玩家金币/魅力/主人/连签，支持管理员操作（加扣金币、
     设魅力、解除奴隶），自动写 `reason=admin` 流水；
   - **动作日志**：服务运行期间的指令与事件（内存最近 500 条，含发送失败、
     WS 断连），更早的查 `data/logs/game.log`；
   - **微信服务状态**：游戏侧（WS、群、最新消息、队列、错误）与部署侧
     （在线、OCR、缓冲、去重计数）实时展示；
   - **游戏配置**：分组编辑全部配置（含礼物目录、打工事件表），保存前校验，
     保存后自动热加载、立即生效（改动写入动作日志）；仅 `api_base_url`、
     `web_host`、`health_port`、`timezone` 四项需重启 game.main 生效。
7. `/health` JSON 接口保留，供脚本监控。

## 本地模拟器（不需要微信）

微信收发服务未部署时，可用内置模拟器测试游戏数据。它绕过 HandWeChat API，
直接向游戏引擎投喂消息，并提供时间推进和调试发金币：

```bash
python -m game.simulator
```

打开 `http://127.0.0.1:8002/`：

- **发消息**：填发信人昵称 + 消息内容（支持 `#` 前缀、全角 `＠`），下方有常用指令快捷键。
- **时间推进**：+1分/+30分/+1小时/+1天 或自定义分钟数，用于测签到连签、打工/反抗冷却、每日额度、魅力衰减。
- **玩家状态**：右侧实时显示每个人的金币、魅力、主人、连续签到（影子玩家带标记）。
- **调试**：给指定玩家直接加金币，方便测高价奴隶购买。
- **重置全部数据**：清空模拟数据库重来。
- **配置可视化**（顶栏入口或 `http://127.0.0.1:8002/config`）：分组查看/编辑全部
  配置项（含礼物目录、打工事件表），保存前经游戏校验器检查，非法配置不会写入
  `config/game_config.json`；正式服务重启后生效。

说明：模拟器默认放开指令间隔/去重/帮助冷却，方便连续点击；打工/反抗冷却与
每日额度仍真实生效。数据使用独立的 `data/sim_game.db`，不影响正式数据；
每发一条消息模拟时间自动前进 1 秒。

## 指令一览

| 系统 | 指令 |
| --- | --- |
| 金币 | `我的金币`、`签到`、`转账@用户名 数量`、`金币榜`、`金币系统` |
| 魅力 | `我的魅力` / `魅力值`、`魅力榜`、`魅力系统` |
| 礼物 | `送礼@用户名 礼物名 [数量]`、`礼物列表`、`礼物榜`、`礼物系统` |
| 奴隶 | `购买奴隶@用户名`、`给他自由@用户名` / `给她自由@用户名`、`奴隶打工`、`我的奴隶`、`我要自由`、`调教@奴隶名`、`调教所有奴隶`、`赎身@用户名`、`奴隶系统` |

- 无参数指令必须整句匹配；带参数指令必须以指令开头且带 `@`。
- 允许可选 `#` 前缀（`#签到` 等价于 `签到`）。
- 与游戏无关的消息一律静默忽略，不回复。

## 拍一拍互动

机器人被拍一拍时自动回复。支持两种消息形式：

- `“{动手拍的人}”拍了拍“{被拍的人}”`
- `“{动手拍的人}”拍了拍“{被拍的人}”{附加消息}`

只有被拍名字与 `bot_name`（或 `bot_name_aliases` 中任一项）精确匹配时才回复，拍其他人
静默忽略。回复文案从 `pat_reply_texts` 随机取一条，支持变量 `{pat}`（动手拍的人）、
`{patted}`（被拍的人）、`{what}`（附加消息，没有时为空串）；同一人
`pat_reply_cooldown_seconds` 秒内只回一次。

拍一拍在 OCR 里是居中系统行，`sender` 会被识别成“我”，因此参与双方全部从正文解析。
只识别带引号的格式，OCR 丢失引号时按普通消息忽略。

## 配置

所有可调参数在 `config/game_config.json`：

- 经济：`initial_coins`（初始 200）、签到奖励、转账手续费 5%、送礼/转账每日额度。
- 魅力：`charm_base` 10，每 `charm_decay_period_days`（7）天衰减 `charm_decay_rate`（10%），
  只衰减超出基础值部分。
- 奴隶：`slave_price_coeff` 2.0、随机系数范围 [0,10]、最低价 10、每主人最多 5 个奴隶、
  打工冷却 30 分钟/每日 8 次、反抗冷却 180 分钟/每日 3 次。
- 调教：`slave_interactions` 互动文案表（每条带褒/贬/中性标签）、金币与魅力变化幅度
  1~5、字段权重（金币/魅力/两者 4/4/2）、冷却 10 分钟/每日 10 次；数值增减方向
  完全随机，与语气相反时回复会加"但…却"。
- 赎身：`ransom_price_coeff`（0~1，默认 1.0），价格 = 目标魅力 × 系数 × 随机[0,3]，
  允许 0 金币；赎身金支付给原主人，冷却 10 分钟/每日 10 次。
- 礼物：`gifts` 目录（价格与魅力），8 种，10~5200 金币。
- 打工事件：`work_events`，权重随机，正/负/零比例 60/30/10。
- 限流：单用户指令间隔 2 秒、帮助冷却 60 秒、出站 15 条/分钟、回复上限 500 字符（超长拆条）。
- 拍一拍：`bot_name` 机器人昵称、`bot_name_aliases` OCR 易混淆写法、`pat_reply_texts`
  回复文案数组（空数组即关闭）、`pat_reply_cooldown_seconds` 每人回复冷却。
- 群：`allowed_groups` 为空表示所有群都处理；否则按规范化群标题白名单。

配置在启动时校验，非法配置拒绝启动。

## 数据

- SQLite：`data/game.db`（WAL），表：`players`、`gift_events`、`coin_ledger`、`daily_counters`。
- 所有金币变动写入 `coin_ledger`，礼物写入 `gift_events`，每日次数写入 `daily_counters`。
- 玩家按 `群标题 + 昵称` 隔离；群标题去掉尾部成员数（如 `(32)`）后作为 `group_key`。
- 从未发言的玩家首次被 @ 时会创建"影子玩家"（`is_phantom=1`），本人发言后自动转正；
  排行榜不显示影子玩家。

## 日志

- `data/logs/game.log`，10MB 轮转，保留 5 份。
- 每条指令一行：`时间 | 级别 | group=... sender=... cmd=... result=... cost_ms=...`。
- 发送任务失败记录 `task_id`、`error_code`、`error_message`。

## 已知限制

1. **昵称含空格的玩家无法被 @ 指令定位**（`@用户名` 只取第一个空格前的 token）。
2. 微信昵称改名后视为新玩家，旧数据不自动迁移。
3. OCR 无法识别昵称时消息 `sender=对方`，会被忽略，该玩家也不会注册。
4. 历史消息不补处理：WebSocket 只推送连接建立之后识别到的新消息，断线期间的消息
   也不补发，避免重放扣费指令。
5. 发送依赖 OCR 回读校验；`SEND_VERIFY_FAILED` 不重试，避免重复发送。
6. 消息缓冲在 API 进程内存中，仅适用于单进程单 worker 部署。
7. 拍一拍只识别带引号的系统行格式；OCR 漏识别引号时不会触发。

## 指令别名

`command_aliases` 配置可为指令添加别名，键为规范指令名、值为别名列表：

```json
"command_aliases": {"购买奴隶": ["购买", "买下"], "签到": ["打卡"]}
```

- 别名对普通形式与 `@用户名 指令` 前缀形式同样生效（`购买@李四` ≡ `购买奴隶@李四`，
  `@李四买下` 同理）；
- 解析按关键字**最长优先**，canonical 关键字不会被子串别名抢占；
- 与已有指令关键字冲突的别名、未知的规范指令名会被忽略；
- 配置页（控制台/模拟器）中该项为 JSON 编辑框，热加载立即生效。

## OCR 空格容错

OCR 常把指令里的空格吞掉（`送礼@是你的益达 玫瑰` → `送礼@是你的益达玫瑰`）。
解析器在解析前去掉消息中的全部空白，再按无空格语法切分：

- `送礼@用户名 礼物名 [数量]`：按礼物目录从**最右侧**匹配礼物名，其后的数字为
  数量，前缀为目标昵称（`送礼@是你的益达玫瑰2` ✓）。
- `转账@用户名 数量`：末尾连续数字为金额（`转账@张三100` ✓）。
- `购买奴隶@用户名`、`给他/她自由@用户名`、`调教@奴隶名`、`赎身@用户名`：目标取 `@` 后整段，按
  "精确 → 忽略大小写 → 已知玩家最长前缀"解析（`购买奴隶@张三谢谢` 会命中
  已有玩家 `张三`）。
- 无参数指令中 OCR 插入的空格无影响（`签 到` ✓）。

残留歧义（OCR 吞空格导致信息缺失，无法完全消除）：

1. `转账` 目标昵称以数字结尾时，尾部数字会被整体当作金额；
2. 目标昵称内部恰好包含礼物名时，按最右侧礼物名切分；
3. 新玩家昵称恰好以已有玩家昵称开头时（群里有"张三"，新人叫"张三丰"），
   粘连解析会误命中老玩家。

## 测试

```bash
python -X utf8 -m pytest game/tests -q
```

111 个用例覆盖：解析器（全角/去重/前缀/标点）、经济与随机公式（固定随机源）、
四大系统全部指令的成功与失败路径、调教互动与"但/却"文案、去重/限流/冷却、多群隔离、
白名单暂停、回复拆分、与假 API 的 HTTP/WebSocket 联调、WS 消息分发与最新消息追踪。

## 运维提示

- 修改配置后需重启服务。
- 需要人工调整金币/魅力/奴隶关系时，直接用 SQLite 客户端改 `data/game.db`
  （服务运行中改动需谨慎，建议停服后操作）。
- OCR 监听由使用端自行启动和维护，本服务不调用 `/api/v1/listener/start`
  和 `/api/v1/attach`；WebSocket 断线（含微信离线、监听未开、API 重启）按
  1/2/5/10/30 秒退避重连。WS 帧不带游标，连接位置由服务端维护，重连后从
  服务端当前进度继续推送，不会再出现「本地存着旧游标收不到消息」。
