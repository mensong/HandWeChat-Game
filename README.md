# 微信群社交游戏服务

基于 HandWeChat 消息网关接入微信的群聊社交游戏，包含
**金币系统、魅力系统、礼物系统、奴隶系统**。完整需求规格见
`微信群社交游戏-开发Prompt.md`。

## 运行环境

- Windows 10/11，与微信、HandWeChat、消息网关同机或网络可达
- Python 3.11+，运行时依赖 `websockets`（见 `requirements.txt`）与
  `handwechat-gateway-sdk`（`pip install handwechat-gateway-sdk`），测试需要 pytest

## 启动

1. 安装依赖：

```bash
pip install -r requirements.txt
```

如果 `handwechat-gateway-sdk` 尚未发布到包索引，改从 HandWeChat 仓库构建 wheel 后安装：
`powershell -ExecutionPolicy Bypass -File packaging/PublishSDK.ps1`，再
`pip install dist\sdk\handwechat_gateway_sdk-<version>-py3-none-any.whl`。

2. 部署侧启动 HandWeChat API 与消息网关（默认 `ws://127.0.0.1:8100`）。本服务
   只连网关，不访问 HandWeChat API。
3. 在网关的 `data/gateway_config.json` 里登记本应用，`id`/`token` 必须与
   `config/game_config.json` 的 `gateway_app_id`/`gateway_token` 一致：

```json
{"id": "social-game", "name": "群游戏", "priority": 100,
 "token": "", "timeout_ms": 1500, "groups": []}
```

`groups` 是网关侧的聊天群白名单，留空表示所有群生效；本服务的 `allowed_groups`
仍在应用侧再做一层过滤。

4. 微信登录，并保持目标群聊在当前聊天窗口打开。
5. 启动游戏服务：

```bash
python -m game.main --config config/game_config.json --db data/game.db --log-dir data/logs
```

6. 服务启动后会自动：连接网关（`WS /api/v1/gateway/ws/app`，握手 `protocol: 2`）→ 在 `hello.rules`
   里上报本服务关心的消息（见「网关规则上报」）→ 用 `welcome.context`
   初始化微信在线、OCR 监听和群标题 → 接收网关逐条下发的 `offer`，只处理
   `is_latest=true` 的消息；有指令命中时回 `consume` 并通过网关代发回复，否则回
   `rewrite` 放行给其他应用。连接建立前的历史消息不会补发。
   收到 `upstream_state` / `chat_changed` 会同步更新在线状态和群标题；每次代发的
   `send_result` 回执用于记录最终发送结果。
7. **Web 控制台**：`http://127.0.0.1:8001/`（`web_host` 默认 `0.0.0.0`，局域网
   可通过本机 IP:8001 访问）：
   - **玩家数据**：各群玩家金币/魅力/主人/连签，支持管理员操作（加扣金币、
     设魅力、解除奴隶），自动写 `reason=admin` 流水；
   - **动作日志**：服务运行期间的指令与事件（内存最近 500 条，含发送失败、
     网关认证失败、上游状态变化），更早的查 `data/logs/game.log`；
   - **运行状态**：网关连接、应用 ID、offer 数、微信在线、OCR 监听、上游连接、
     当前群与发送失败数实时展示；
   - **游戏配置**：分组编辑全部配置（含礼物目录、打工事件表），保存前校验，
     保存后自动热加载、立即生效（改动写入动作日志）；仅 `gateway_url`、
     `gateway_app_id`、`gateway_token`、`gateway_rules`、`web_host`、`health_port`、
     `timezone` 需重启 game.main 生效。
8. `/health` JSON 接口保留，供脚本监控。

## 本地模拟器（不需要微信）

微信收发服务未部署时，可用内置模拟器测试游戏数据。它绕过 HandWeChat API，
直接向游戏引擎投喂消息，并提供时间推进和调试发金币：

```bash
python -m game.simulator
```

打开 `http://127.0.0.1:8002/`：

- **发消息**：填发信人昵称 + 消息内容（支持 `#` 前缀、全角 `＠`），下方有常用指令快捷键。
- **时间推进**：+1分/+30分/+1小时/+1天 或自定义分钟数，用于测签到连签、打工/反抗冷却、每日额度、魅力衰减。
- **玩家状态**：右侧实时显示每个人的金币、魅力、主人、连续签到（影子玩家带标记）。
- **调试**：给指定玩家直接加金币，方便测高价奴隶购买。
- **重置全部数据**：清空模拟数据库重来。
- **配置可视化**（顶栏入口或 `http://127.0.0.1:8002/config`）：分组查看/编辑全部
  配置项（含礼物目录、打工事件表），保存前经游戏校验器检查，非法配置不会写入
  `config/game_config.json`；正式服务重启后生效。

说明：模拟器默认放开指令间隔/去重/帮助冷却，方便连续点击；打工/反抗冷却与
每日额度仍真实生效。数据使用独立的 `data/sim_game.db`，不影响正式数据；
每发一条消息模拟时间自动前进 1 秒。

## 指令一览

| 系统 | 指令 |
| --- | --- |
| 金币 | `我的金币`、`签到`、`转账@用户名 数量`、`金币榜`、`金币系统` |
| 魅力 | `我的魅力` / `魅力值`、`魅力榜`、`魅力系统` |
| 礼物 | `送礼@用户名 礼物名 [数量]`、`礼物列表`、`礼物榜`、`礼物系统` |
| 奴隶 | `购买奴隶@用户名`、`给他自由@用户名` / `给她自由@用户名`、`奴隶打工`、`我的奴隶`、`我要自由`、`调教@奴隶名`、`调教所有奴隶`、`赎身@用户名`、`奴隶系统` |

- 无参数指令必须整句匹配；带参数指令必须以指令开头且带 `@`。
- 无参数指令可直接 @ 机器人：`签到`、`@机器人签到`、`签到@机器人` 三种写法等价；
  机器人名取 `bot_name`，OCR 误读或群昵称不同时写进 `bot_name_aliases`。
- 允许可选 `#` 前缀（`#签到` 等价于 `签到`）。
- 与游戏无关的消息一律静默忽略，不回复。

## 自动回复规则（auto_replies）

在配置里按顺序配置正则规则，消息匹配到某条规则时直接回复设定文案（规则优先于内置指令）。
匹配前会做 NFKC 规范化并删除全部空白，OCR 在字间插入的空格不影响正则。

每条规则字段：

| 字段 | 说明 |
| --- | --- |
| `name` | 规则名（日志与冷却标识，可省略，默认 `规则N`） |
| `enabled` | 是否启用，默认 `true` |
| `pattern` | Python 正则，`re.search` 匹配；写错会在保存/加载时报错 |
| `replies` | 回复文案：字符串或数组（数组等概率随机取一条） |
| `cooldown_seconds` | 冷却秒数，0 = 不限 |
| `cooldown_key` | 冷却键模板，默认 `{sender}`；同一规则 + 群 + 键值在冷却内只回一次 |
| `allow_ignored_senders` | 是否处理 `ignore_senders` 里的发送者，默认 `false` |

回复文案支持变量：

- `{sender}`：发送者
- `{bot}`：机器人昵称（`bot_name`）；加载配置时替换，所有配置字符串都可用，`pattern` 内自动转义
- `{msg1}`、`{msg2}`…`{msgN}`：正则第 N 个捕获组；消息缺少该部分时为空串
- 不存在的变量原样保留

拍一拍就是默认配置里的一条规则：`“A”拍了拍“机器人昵称”` 时回复。引号兼容 `""`、`''`、
`‘’` 和 `「」『』`，且开闭引号写在同一个字符集里，OCR 把开、闭引号识别反了也能命中。
拍一拍在 OCR 里是
居中系统行，`sender` 会被识别成“我”，所以该规则需开启 `allow_ignored_senders`。
默认规则用 `({bot})` 匹配机器人昵称；OCR 易混淆的昵称可以写成 `({bot}|饭人徽蔓)`。

## 网关规则上报（hello.rules）

新版网关支持应用在握手时上报 `rules`：先按「聊天群 + 规则」筛出候选应用，再按优先级
逐个询问，没命中的应用根本收不到消息。本服务在 `hello` 里上报规则，把本应用真正会处理的
指令、`@用户名` 形式和启用的自动回复告诉网关。

- **默认自动生成**：`gateway_rules` 为 `null` 时，按解析器指令表、`command_aliases`
  和启用中的 `auto_replies` 推导（当前 4 条），指令或别名改了规则自动跟着变。
  但规则只在启动时生成并随连接上报：改 `auto_replies`、别名或 `gateway_rules` 后
  需要重启 game.main，热加载只更新应用侧匹配，不会把新规则推给网关。
- **手写覆盖**：`gateway_rules` 填非空数组则原样上报；保存配置时按网关同一套上限校验
  （≤32 条、正则 ≤200 字符、每个列表 ≤32 项、`chat_types` 只支持 `group` / `friend`）。
  规则随连接上报，修改后需重启 game.main。
- **写法是前缀匹配**：指令用 `^[#＃]?\s*签到` 这类前缀正则，只容忍行首空白和 `#` 后空格；
  字间、匹配单元之间不插空白，规则更短。OCR 若在指令中间插了空格，网关不会下发到应用
  （应用侧解析仍会去空白，但消息已被挡在网关）。
  宁可多放行（应用侧仍会 `rewrite`），不能把要处理的消息挡在网关。
- `"gateway_rules": []` 表示全部匹配，只有兜底/通用机器人才这样配，业务应用不要用。
- 运行状态里 `gateway.rules` 显示来源（`auto` / `config`）和条数；排查「收不到消息」时，
  先看网关 `/api/v1/gateway/status` 的 `apps[].rules.mode` 和 `apps[].groups`。
- 规则表达不了 `is_latest`、`ignore_senders`、冷却等条件，这些仍在应用侧判断；置顶期间
  网关会绕过规则下发同一聊天群的全部消息，`on_offer` 的 `rewrite` 兜底照旧。
- **聊天金币影响**：`chat_coins_per_message` 只对真正下发到应用的消息生效。普通闲聊
  不再经过网关的规则筛选，因此不会再产生聊天收入，指令类消息照常。

## 配置

所有可调参数在 `config/game_config.json`：

- 经济：`initial_coins`（初始 200）、签到奖励、转账手续费 5%、送礼/转账每日额度。
- 魅力：`charm_base` 10，每 `charm_decay_period_days`（7）天衰减 `charm_decay_rate`（10%），
  只衰减超出基础值部分。
- 奴隶：`slave_price_coeff` 2.0、随机系数范围 [0,10]、最低价 10、每主人最多 5 个奴隶、
  打工冷却 30 分钟/每日 8 次、反抗冷却 180 分钟/每日 3 次。
- 调教：`slave_interactions` 互动文案表（每条带褒/贬/中性标签）、金币与魅力变化幅度
  1~5、字段权重（金币/魅力/两者 4/4/2）、冷却 10 分钟/每日 10 次；数值增减方向
  完全随机，与语气相反时回复会加"但…却"。
- 赎身：`ransom_price_coeff`（0~1，默认 1.0），价格 = 目标魅力 × 系数 × 随机[0,3]，
  允许 0 金币；赎身金支付给原主人，冷却 10 分钟/每日 10 次。
- 礼物：`gifts` 目录（价格与魅力），8 种，10~5200 金币。
- 打工事件：`work_events`，权重随机，正/负/零比例 60/30/10。
- 限流：单用户指令间隔 2 秒、帮助冷却 60 秒、出站 15 条/分钟、回复上限 500 字符（超长拆条）。
- 网关：`gateway_url`、`gateway_app_id`、`gateway_token`，需与网关配置的
  `apps[]` 一致；`token` 为空表示不校验。`gateway_rules` 为 `null` 时自动生成
  握手规则，填数组则手写覆盖（见「网关规则上报」）。
- 自动回复：`bot_name` 机器人昵称（配置中所有字符串可用 `{bot}` 引用，
  `pattern` 内自动转义；为空但被引用时拒绝启动/保存）、`bot_name_aliases`（@机器人 指令
  额外识别的昵称数组）、`auto_replies` 正则回复规则数组（见上节），拍一拍也是其中一条。
- 群：`allowed_groups` 为空表示所有群都处理；否则按规范化群标题白名单。

配置在启动时校验，非法配置拒绝启动。

## 数据

- SQLite：`data/game.db`（WAL），表：`players`、`gift_events`、`coin_ledger`、`daily_counters`。
- 所有金币变动写入 `coin_ledger`，礼物写入 `gift_events`，每日次数写入 `daily_counters`。
- 玩家按 `群标题 + 昵称` 隔离；群标题去掉尾部成员数（如 `(32)`）后作为 `group_key`。
- 从未发言的玩家首次被 @ 时会创建"影子玩家"（`is_phantom=1`），本人发言后自动转正；
  排行榜不显示影子玩家。

## 日志

- `data/logs/game.log`，10MB 轮转，保留 5 份。
- 每条指令一行：`时间 | 级别 | group=... sender=... cmd=... result=... cost_ms=...`。
- 网关 `send_result` 回执 `final=true` 且失败时记录样式与错误码，同时写入动作日志。

## 已知限制

1. **昵称含空格的玩家无法被 @ 指令定位**（`@用户名` 只取第一个空格前的 token）。
2. 微信昵称改名后视为新玩家，旧数据不自动迁移。
3. OCR 无法识别昵称时消息 `sender=对方`，会被忽略，该玩家也不会注册。
4. 历史消息不补处理：网关只下发在线实时消息，连接前与断线期间的消息都不补发，
   避免重放扣费指令。
5. 发送最终结果依赖网关的 `send_result` 回执；回执超时或网关未推最终结果时，
   只能查 `gateway.log`。
6. 消息缓冲在 API 进程内存中，仅适用于单进程单 worker 部署。
7. 拍一拍只识别带引号的系统行格式；OCR 完全没有引号或输出未列出的引号字符时不会触发。
8. 网关按上报规则筛选后，普通闲聊不再下发到本服务：聊天金币只对命中规则的消息发放，
   规则没覆盖的自动回复也不会触发——新增自动回复规则时，`gateway_rules` 为 `null`
   会自动带上，手写覆盖时需自行同步。

## 指令别名

`command_aliases` 配置可为指令添加别名，键为规范指令名、值为别名列表：

```json
"command_aliases": {"购买奴隶": ["购买", "买下"], "签到": ["打卡"]}
```

- 别名对普通形式与 `@用户名 指令` 前缀形式同样生效（`购买@李四` ≡ `购买奴隶@李四`，
  `@李四买下` 同理）；
- 解析按关键字**最长优先**，canonical 关键字不会被子串别名抢占；
- 与已有指令关键字冲突的别名、未知的规范指令名会被忽略；
- 配置页（控制台/模拟器）中该项为 JSON 编辑框，热加载立即生效。

## OCR 空格容错

OCR 常把指令里的空格吞掉（`送礼@是你的益达 玫瑰` → `送礼@是你的益达玫瑰`）。
解析器在解析前去掉消息中的全部空白，再按无空格语法切分：

- `送礼@用户名 礼物名 [数量]`：按礼物目录从**最右侧**匹配礼物名，其后的数字为
  数量，前缀为目标昵称（`送礼@是你的益达玫瑰2` ✓）。
- `转账@用户名 数量`：末尾连续数字为金额（`转账@张三100` ✓）。
- `购买奴隶@用户名`、`给他/她自由@用户名`、`调教@奴隶名`、`赎身@用户名`：目标取 `@` 后整段，按
  "精确 → 忽略大小写 → 已知玩家最长前缀"解析（`购买奴隶@张三谢谢` 会命中
  已有玩家 `张三`）。
- 无参数指令中 OCR 插入的空格在解析阶段无影响（`签 到` ✓）。注意：上报给网关的规则
  只在行首与锚点处容忍空白，字间带空格的消息可能在下发前就被过滤掉。

残留歧义（OCR 吞空格导致信息缺失，无法完全消除）：

1. `转账` 目标昵称以数字结尾时，尾部数字会被整体当作金额；
2. 目标昵称内部恰好包含礼物名时，按最右侧礼物名切分；
3. 新玩家昵称恰好以已有玩家昵称开头时（群里有"张三"，新人叫"张三丰"），
   粘连解析会误命中老玩家。

## 运维提示

- 修改配置后需重启服务。
- 需要人工调整金币/魅力/奴隶关系时，直接用 SQLite 客户端改 `data/game.db`
  （服务运行中改动需谨慎，建议停服后操作）。
- OCR 监听由使用端自行启动和维护，本服务不访问 HandWeChat API；网关断线（含
  微信离线、网关重启）由 SDK 每 3 秒自动重连，不可恢复的关闭码
  （4009/4400/4401/4404）记录后停止重连，修好网关配置后重启 game.main。
  群标题与在线状态来自网关的 `welcome.context`、`upstream_state` 和
  `chat_changed` 推送。
